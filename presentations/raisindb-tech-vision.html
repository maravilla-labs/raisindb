Consistency · the hard partEventual consistency and locking

The map converges. The last seat is decided.

Most state wants availability: let every node take writes and reconcile later. Some state cannot be reconciled at all — it has to be decided once. RaisinDB ships both primitives and makes you choose per workload, instead of forcing one model on everything.

This is the slide the architects came for. Slow down. The metaphor first: “A sensor reading, a document edit, a tag — those converge. The last seat on a flight does not converge; someone has to be told no.” Then the mechanism in one breath each: CRDT + Hybrid Logical Clock for causal order; lease returns a monotonic fencing token so a process that froze and woke up can't overwrite newer state. Say the honest caveat out loud — the in-process lock backend is single-node; a multi-node cluster must use Redis or it will oversell, and the server logs a warning if you get it wrong. Volunteering a limitation here buys more credibility than any benchmark. Appendix A3 has the API.

Integration · virtual nodesMount the outside world as nodes

An external system becomes a subtree. Everything downstream just works.

The enterprise-architect unlock. The standing objection to any new database is “our data lives in eleven other systems.” Answer: mount them. An external system becomes a subtree at a path you choose; because the sync engine writes through the normal transactional path, the mounted items are ordinary nodes — so triggers, SQL, full-text, vector, audit, row-level security and replication all apply with no new machinery. Then the economics: an adapter is a sandboxed function shipped in a package, so customers and partners write their own. We don't have to build 200 connectors to be useful. Google Drive ships built-in as the reference implementation.

Agents & workflowsFunctions, agents and humans are the same step

The “why now” slide. Everyone is assembling an agent stack out of a vector store, a workflow engine, a message queue and a scratch database — and then discovering they can't answer “why did the agent do that?” because the evidence is in four systems with four retention policies. The problem everyone hits

Yesterday's positions are today's read cost

The revision is part of the index key, so a vehicle circling one airport piles up superseded entries in the same coarse cell — a query that was milliseconds on day one becomes seconds on day two. A stateful compaction filter drops them, keeping a hot cell constant instead of growing with update count. On by default.

Use this as proof of engineering depth, not as a feature list. The compaction-filter story is the tell: it's the kind of problem you only find by actually running a tracking workload, and the kind of fix a bolted-on extension can't make because it doesn't own the storage engine. Appendix A2How concurrent writes resolve

Deterministic merge, in any order.

OperationResolution
PropertiesLast-write-wins — vector clock, then timestamp, then node id as tie-break
RelationsAdd-wins set — an addition beats a concurrent deletion
DeletesDelete-wins — a deleted node cannot be resurrected
MovesLast-write-wins, and a conflict event is emitted
Mode 01 · immediate

Real-time push

Fires after transaction commit, over TCP with MessagePack framing. Typically 10–50 ms depending on link latency.

Mode 02 · safety net

Periodic pull

Each node compares its own vector clock against each peer and pulls what it is missing. Default interval 30 s, batch 1000 operations. Survives a push that never landed.

Ordering

Causal, not wall-clock

Operations apply in happens-before order via Hybrid Logical Clock, so a node whose clock drifts cannot reorder someone else's causally-later write.

If asked “is this Raft?” — no, and deliberately. Raft gives you linearizability at the cost of a quorum, which a disconnected gateway cannot form. We take availability at every tier and pay for it with explicit coordination only where it is actually required.
Appendix A3Locks, leases and inventory

Coordination, and what it costs.

// lease with a monotonic fencing token
const t = await raisin.locks.acquire(key, owner, ttl);
// t === null → someone else holds it. No queue.

// counting reservation — the "N seats left" primitive
await raisin.inventory.claim(pool, 2, capacity);
// atomic decrement, never below zero
Why the token

A frozen holder cannot clobber newer state

The token is monotonic and travels with the guarded write. The writer rejects anything below the highest token it has seen — so a process that paused for 40 seconds and woke up holding an expired lease is refused, not obeyed.

Say this before they ask

In-process locks are single-node

A multi-node cluster must configure the Redis backend or it will oversell. The server logs a warning when it sees in-process locks together with replication — but the correct answer is configuration, not a warning.

SurfaceCall
Functionsraisin.locks.* · raisin.inventory.*
WebSocketlocks_acquire · inventory_claim
HTTPPOST /api/{repo}/{branch}/locks/acquire

Contention returns 409, not a wait. A caller that must queue rather than fail uses the in-process keyed mutex instead — a different primitive, chosen deliberately.

The distinction worth drawing: reject on contention (lease) versus queue on contention (keyed mutex). Choosing the wrong one is how ticket systems oversell and how workflow engines double-execute.

Appendix A6What a tracking workload actually costs

Precision count is a write-cost knob.

Counter-intuitive

Coarse cells are where read cost concentrates

A vehicle circulating one airport never leaves its coarse cell, so that single prefix accumulates roughly two entries per position update. At fine precision the entries spread thin and cost nothing.

Bounded by

A stateful compaction filter

Superseded entries are dropped during compaction — the descending revision sits immediately after the geohash in the key, so they are identifiable. On by default. Without it, one vehicle at 1 Hz reaches ~10⁵ entries in a single coarse prefix inside a day.

Beyond about 10 km a precision-6 ring approaches the 1024-cell scan budget and the planner declines the index — degrading to a correct full scan with a warning, never to a wrong answer.

The last sentence is the one to say out loud: the planner degrades to slow and correct, never to fast and wrong. That's the design rule across the engine.

Appendix A8Tenancy · security · secrets

Enforced at the write layer, not in a service class.

Tenancy

Prefix isolation

Tenant, repo, branch and workspace are part of every key. A scoped storage wrapper makes the prefix non-optional, so a query cannot accidentally escape its tenant.

Authorisation

Row-level security

Conditions evaluated below every protocol — REST, WebSocket and psql alike. Reaching for the SQL wire does not get you a bypass.

Secrets

Plaintext never leaves

A schema field marked encrypted is moved into an encrypted store on write and the property is rewritten to a secret:// reference. Reads never resolve it — which is why the reference is safe in an API response, a SQL result, an audit entry and a replication payload alike.

Ordering matters

Vault before index

If the value were indexed first, the plaintext's hash would sit in the property index permanently — turning an equality filter into a guessing oracle. Vaulting happens after validation and before every index call.

Failure mode

Fail closed

Neighbouring subsystems fail open by design. This one refuses the write on any doubt, because the alternative is plaintext on disk.

Audit

Two independent records

MVCC revision history is structural and always on. The audit log is opt-in per NodeType and records the resolved actor, stamped at the transaction layer.

The line that matters to a regulated buyer: a stolen RocksDB backup is inert, because the root key is not in the database. The line that matters to an engineer: enforcement is at the write layer, because SQL DML and the WebSocket handler write straight to the transaction context and would bypass anything placed in a service class.
