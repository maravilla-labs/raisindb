# WebAssembly functions in TypeScript

The TypeScript SDK is `@raisindb/function-wasm` (`sdks/ts/function-wasm`), built
on [jco] / [ComponentizeJS]. Its design goal is blunt: **a QuickJS function
componentizes with zero source changes.**

That is not a claim about similarity. The SDK's `api_wrapper.js` is a
byte-identical copy of the QuickJS runtime's own wrapper — regenerated by
`make gen-bindings`, guarded by a freshness test — so the frozen per-method
error conventions (throw vs `null` vs `[]` vs a sentinel) are literally the same
code running in both runtimes. All the SDK adds is the three globals that
wrapper reaches for, mapped onto the WIT host.

```bash
raisindb create function greet --lang ts
```

## A function

```js
// src/index.js — no SDK import, no registration call
export async function handler(input) {
  const people = raisin.nodes.getChildren('content', '/people');
  console.log('greeting', input.name);
  return { greeting: `Hello, ${input.name}!`, people: people.length };
}

// One module, many handlers: entry_file main.wasm:shout picks this one.
export async function shout(input) {
  return { greeting: `Hello, ${input.name}!`.toUpperCase() };
}
```

The export named `handler` is the handler `default` — i.e. a bare
`entry_file: main.wasm`. Any other name maps to the export of the same name, so
`main.wasm:on-order` calls `onOrder` (or `'on-order'`). That is exactly the
`index.js:handlerName` grammar QuickJS functions already use.

## Build

```bash
npx raisin-wasm-build src/index.js --out main.wasm
```

which wraps `jco componentize` with the flags that are known to work (verified
against jco 1.32.1 / componentize-js 0.22.0). Your module is never
componentized directly: the build writes a small entry that imports it, wraps it
with `createHandler`, and imports the one module that references the WIT host.

Expect an **8–12 MB** artifact — a component embeds the whole StarlingMonkey JS
engine. The server's default cap is 32 MiB, and one artifact can back N Function
nodes (`entry_file: ../greet-ts/main.wasm:shout`), which is how a package with
twenty handlers still ships twelve megabytes instead of two hundred.

## Testing, natively

```js
import { createMockHost } from '@raisindb/function-wasm/testing';
import { createHandler } from '@raisindb/function-wasm';
import * as fn from '../src/index.js';

const mock = createMockHost({ context: { tenant_id: 't1' } });
mock.expect('nodes_getChildren', () => [{ path: '/people/ada' }]);
mock.install();

const out = await createHandler(fn)('default', JSON.stringify({ name: 'Ada' }));
```

`vitest run` — no wasm build, no server.

## What is not available

The runtime is StarlingMonkey with `http` and `fetch-event` disabled, driven by
a synchronous host. It is not Node, and it is not the full QuickJS environment.

| Missing | Use instead |
|---|---|
| `fetch`, `Request`, `Response`, `Headers` | `raisin.http.fetch(...)` — the only egress the host polices |
| `setTimeout` / `setInterval` / timer-based waits | nothing: there is no scheduler after the export returns |
| `Resource.resize` / `toImage` / `getPageCount` | `raisin.assets.*`, or keep that function in JavaScript. These need the server's per-execution temp files; calling one throws **by name** rather than `undefined is not a function` |
| `require`, `node:*`, the filesystem | zero preopens; no `wasi:sockets`, no `wasi:http` |
| dynamic `import()` of a module absent at build time | everything is snapshotted at componentize time |

`async`/`await` **does** work: ComponentizeJS runs the event loop to resolution
around the export call. What does not work is waiting on something nobody will
resolve — a timer, a socket, a dangling promise: the component simply returns.

`console.*` is forwarded to the host log (`ExecutionResult.logs` and the SSE log
stream). `Date.now()` and `Math.random()` work — `clocks` and `random` stay
linked.
