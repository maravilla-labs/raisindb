## Finding 1 — mail: the adapter is stale, and the v0.2.17 update path cannot reach it

### The symptom chain

`max_items_per_sync` is 1000. Every delta run enumerates the mailbox **from the
beginning**, processes 1000 already-imported messages, hits the cap, and stops —
so it never reaches recent mail. The console shows exactly that:

```
Last run: Manual · Delta · OK · 53s · 0 written / 1000 skipped / no changes
Import progress: 20,763 items imported · Full walk complete
```

`delta.rs` is correct and running:

```rust
// crates/raisin-rocksdb/src/jobs/handlers/virtual_mount_sync/delta.rs:54
let want_baseline = token.is_none() && state.backfill_complete;
// …
let params = json!({ "since_token": token, "folder_id": …, "baseline_only": want_baseline });
```

With `backfill_complete = true` and no token, `want_baseline` is `true`, so the
binary asks for a baseline. The **JavaScript adapter that receives that flag has
never heard of it**, builds a plain `/messages/delta` URL, and Graph performs a
full initial enumeration. Rust half shipped; JS half did not.

### Why it did not ship — the actual defect

Adapter code is **package content**, living in the repo as a `raisin:Function`
node. It is written when the package's content is installed. v0.2.17 added a
staleness check so an already-installed package gets updated content:

```rust
// crates/raisin-server/src/builtin_package_init_handler.rs:228
let stale = self.package_content_is_stale(tenant_id, repo_id,
                &package_info.manifest.name, &package_info.content_hash).await;
let install_content = package_info.manifest.auto_install || stale;
```

`package_content_is_stale` ends with:

```rust
match self.system_update_repo
    .get_applied(tenant_id, repo_id, ResourceType::Package, package_name).await
{
    Ok(Some(applied)) => applied.content_hash != content_hash,
    // "Installed but never recorded: predates applied-hash tracking …"
    _ => false,
}
```

**That fallback is the hole.** In production nothing ever writes an applied-hash
record for a package an operator installed on demand. The only production
`set_applied` call sites are:

- `builtin_package_init_handler.rs:266` — gated on `install_content`, which for
  an `auto_install: false` package was **always false before v0.2.17**, so it
  never ran;
- `raisin-core/src/system_updates/apply.rs:91,148` and
  `raisin-transport-http/src/handlers/system_updates/apply_package.rs:167` — the
  system-updates flow, a different feature.

The on-demand install path — `POST …/{pkg}/raisin:install`,
`handlers/packages/commands.rs:79` → `install::install_package_impl` — records
**nothing**. (`builtin_package_init_handler.rs:900` is inside a `#[cfg(test)]`
module; it is not a production call site.)

So for `ms-graph-adapter`: installed by the operator ⇒ no applied record ⇒
`get_applied` returns `Ok(None)` ⇒ `_ => false` ⇒ never stale ⇒ never updated.
The conservative branch guards precisely the case the check was written for.

### Blast radius of the correct fix

Treating "installed, but no applied record" as stale affects exactly the
packages that opt out of auto-install:

```
ai-tools                auto_install=unset  modes=[merge]
google-calendar-adapter auto_install=false  modes=[merge,skip]
google-drive-adapter    auto_install=false  modes=[merge,skip]
imap-adapter            auto_install=false  modes=[merge,skip]
ms-graph-adapter        auto_install=false  modes=[merge,skip]
raisin-integrations     auto_install=true   modes=[merge]
raisin-mcp-client       auto_install=true   modes=[default]
…everything else        auto_install=unset (defaults true — already installs every boot)
```

The four connector adapters, and only those. Their manifests are already built
for repeated content updates — `merge` for the adapter/mapper functions,
`skip` for the operator's live config node, with this comment in
`builtin-packages/ms-graph-adapter/manifest.yaml`:

> `merge` re-applied the shipped template over it and reset every one of those
> to the packaged defaults — observed in production as a configured Microsoft
> connector reverting to `client_id: ""`, no secret, zero accounts … `skip` is
> documented for exactly this. **The adapter and mapper functions above stay
> `merge` — those are OUR code and MUST keep updating, which is what gets a
> connector fix to a running deployment.**

That is the intended design; the boot path simply never exercised it. Installing
once records the hash, so the behaviour converges after a single boot.

### Immediate remedy without a release

Re-install the package into the affected repo with `mode=sync` (updates existing
content, creates what is new, leaves the rest alone — exposed in the console,
`api/packages.ts:307`):

```
POST /api/packages/{repo}/main/head/ms-graph-adapter/raisin:install?mode=sync
```

Then **Stop** the mail mount to discard the enumeration cursor, and let the next
delta re-baseline.

### Verification that settles it

Only one check counts: after the adapter is updated and the mount is stopped, a
delta run reports **far fewer than 1000 skipped**, and a newly sent email
appears. Every intermediate signal so far has been consistent with both a
working and a broken system.

## Finding 2 — calendar: two bugs stacked, the outer one now fixed

### Outer (fixed in v0.2.17): QuickJS pool OOM

Reported as `Failed to setup JS environment: out of memory` and, on other runs,
the bare `Exception generated by QuickJS`. **Those are the same failure** — the
latter is what you see when QuickJS is left in an exception *state* with no
exception *object* for `ctx.catch()` to describe, so the message fell back to
rquickjs's fixed Display string.

Two compounding defects in `crates/raisin-functions/src/runtime/quickjs/pool.rs`:

1. **`set_memory_limit` is runtime-global; the limit is per function.** Pool
   invariant 4 re-set the limit every execution so no tenant inherited another's
   ceiling — but the pooled runtime still carried the previous occupant's
   allocations. Stamping a modest function's ceiling onto a runtime already
   above it does not shrink it; it guarantees the next allocation fails. The
   invariant was not merely insufficient, it was the mechanism.
2. **Nothing ever called `run_gc`.** QuickJS reclaims cycles only on demand, and
   a fresh full context per execution makes cycles ordinary, so a runtime
   accumulated across up to 500 executions uncollected.

Intermittent because it depended on which runtime the pool handed out — which is
why it landed on the quiet calendar mount while the busy mail mount churned the
pool beside it.

`checkout` now takes the limit the execution will run under, collects a reused
candidate, measures it, and discards one retaining more than half the incoming
budget. Reproduced in a unit test before fixing
(`Allocation failed while creating object`), and the test fails without the vet.

**Confirmed fixed in production: the message no longer appears.**

### Inner (open): the workspace does not allow `raisin:Event`

With the OOM gone, the real error is visible — repeating steadily:

```
2026-08-05T07:00:57Z WARN raisin_rocksdb::jobs::handlers::virtual_mount_sync::materializer:
  virtual mount item rejected; continuing with the rest of the batch
  mount_id=Dg1PE4m14XBmPt24bpuuT
  external_id=AAMkADVlMDc4NmY5…
  error=Validation failed: Workspace 'stories' does not allow nodes of type 'raisin:Event'.
    Allowed types: ["studio:Folder", "studio:PolicyFolder", "studio:BlueprintFolder",
      "studio:Story", "studio:Page", "studio:PageVariation", "studio:Policy",
      "studio:SiteGroup", "raisin:Folder", "raisin:Node", "raisin:Mail", "raisin:Asset"]
```

Note `raisin:Mail` **is** allowed and `raisin:Event` is **not** — which is
exactly why mail materializes and calendar does not. That asymmetry looks like
`raisin:Mail` was added by hand when the mail mount was set up.

`ms-graph-adapter`'s `workspace_patches` only patch `raisin:system`:

```yaml
workspace_patches:
  functions:
    default_folder_type: raisin:Folder
  "raisin:system":
    default_folder_type: raisin:Folder
    allowed_node_types:
      add: [raisin:Integration, raisin:VirtualMount]
```

The **target** content workspace is never patched — and cannot be from the
manifest, because the operator chooses it at mount time, not install time.

**Immediate remedy:** add `raisin:Event` to the `stories` workspace's allowed
node types in the admin console.

**Proper fix (not done):** creating or enabling a virtual mount should ensure
the target workspace accepts the node types the mapper produces, or fail loudly
at mount creation. Today it is a per-item `WARN` and a run that reports
`OK · 100 failed` — a mount that cannot ever work, presented as healthy.

## Finding 3 — the calendar sync job exceeds the 600 s ceiling and retries forever

```
2026-08-05T07:10:51Z WARN raisin_rocksdb::jobs::watchdog: Job timed out
  job_id=LyxTO7kJbxgSxZxkQ_PVR
  job_type=VirtualMountSync(Dg1PE4m14XBmPt24bpuuT/delta/push)
  running_seconds=610 heartbeat_stale_seconds=Some(0) timeout_seconds=600
  retry_count=0 max_retries=3 will_retry=true
```

`heartbeat_stale_seconds=0` — the job is alive and heartbeating. It is reaped on
**wall clock**, not staleness (`TimeoutWatchdog`). It spends ten minutes pushing
items that can never be accepted (Finding 2), gets killed, and retries.

Likely resolves once Finding 2 is fixed, but the underlying shape is worth
noting: a mount whose every item is rejected burns the full job budget and
retries three times, and nothing surfaces that as a failure.

## Finding 4 — `RUST_LOG=error` hides the diagnostics we ship

```
RUST_LOG=error
```

Consequences observed today:

- The v0.2.17 update line (`"Installed package content is out of date; updating
  it in place"`, INFO) **could never appear** — its absence proved nothing, and

  invisible.

Recommend `RUST_LOG=warn,raisin_rocksdb::jobs=info,raisin_server::builtin_package_init_handler=info`

Every boot, at ERROR, for four tenant/repo pairs:

```
2026-08-05T07:00:20Z ERROR raisin_server::builtin_package_init_handler:
  Failed to install builtin package tenant_id="6a0afb9e84e4b48ed2fa4b4c" repo_id="ttt"
```

Packages: `ai-tools`, `raisin-auth`, `raisin-messaging`, `raisin-relationships`,
`raisin-social`, `raisin-stewardship`.
Repos: `6a0afb9e84e4b48ed2fa4b4c/{ttt,website,xxxx}` and `default/website`.

An install that finds its own package node already present is the **normal**
steady state, not an error. This is almost certainly the create-path probe
issue: the existence probe is HEAD-bounded but the id-uniqueness check is not,
so a node stranded above HEAD is permanently unwritable. 24 ERROR lines per
boot. Unrelated to the mount work, but it is why the log is hard to read.

## Finding 6 — webhook delivery counters stay at zero while webhooks demonstrably arrive

The console shows `No delivery yet · ACCEPTED 0 · REJECTED 0`, with the
subscription `active`, while the run history on the same page lists
`Webhook · Delta · OK` runs. Both cannot be true.

They come from the same handler, in this order
(`crates/raisin-transport-http/src/handlers/integrations/notifications.rs:133`):

```rust
record_delivery(&state, &tenant.tenant_id, &repo, &mount.id, true).await;
// 4. Enqueue a delta sync … and ack immediately
enqueue_delta_sync(&state, &tenant.tenant_id, &repo, &mount.id).await
```

So a `Webhook`-triggered run in history **proves** `record_delivery` ran. The
counter write is therefore being lost, not skipped.

### Three ways it can be lost, all silent

1. **`record_push_delivery` returns `Ok(false)` with no log at all**
   (`virtual_mount_sync/mod.rs:1166`):
   ```rust
   let Some(node) = svc.get(mount_id).await? else {
       return Ok(false);          // <- no tracing, no counter, no trace
   };
   ```
   and its caller only logs the `Err` case:
   ```rust
   if let Err(e) = raisin_rocksdb::record_push_delivery(…).await {
       tracing::warn!(…, "failed to record push delivery health");
   }
   ```
   `Ok(false)` — the "it did not happen" answer — is discarded by both sides.
   That is an observability defect independent of the cause.

2. **The two branch resolutions in this handler disagree by construction.**
   The mount LOOKUP goes through `config_service`, hardcoded to
   `CONFIG_BRANCH = "main"` (`integrations/mod.rs:98`), with this note in the
   file:
   > `config_service` above is still hardcoded, because it is a sync fn with
   > many callers.

   The delivery WRITE goes through `config_branch(state, tenant, repo)`
   (`integrations/mod.rs:114`), which resolves the repo's real
   `config.default_branch`. On any repo whose default branch is not `main`, the
   lookup finds the mount and the write targets a branch where it does not
   exist ⇒ `Ok(false)` ⇒ silence. This is the "mirrored paths that drift" class
   again — two answers to "which branch" in one request.

   **Unconfirmed for this deployment**: `default/website` most likely does have
   `main` as its default branch, in which case this is a latent bug and not
   today's cause. Worth fixing regardless.

3. **`persist_mount_state` compare-and-set refuses the write.** It skips when
   `stored_seq > state.state_seq` ("another writer advanced this mount's
   state"). A delivery arriving mid-sync races the sync's own progress writes.
   This one *does* `warn!`.

All three are invisible at `RUST_LOG=error` (Finding 4). Raising the log level
distinguishes them in one webhook delivery.

## Finding 7 — the sync handler has outgrown its own convention

`CLAUDE.md` says *"Keep files under 300 lines, split into modules as needed."*
The sync tree:

```
2257  virtual_mount_sync/tests.rs
1337  virtual_mount_sync/mod.rs          <- 4.5x
1178  virtual_mount_sync/materializer.rs <- 3.9x
 926  virtual_mount_sync/config.rs       <- 3.1x
 429  virtual_mount_sync/adapter.rs
 337  virtual_mount_sync/full.rs
 302  virtual_mount_sync/check.rs
```

This is not cosmetic, and it is not unrelated to the findings above. `mod.rs`
holds the job entry point, state persistence, push-delivery recording, lease
handling, skip results and run-history bookkeeping in one file — which is why
`record_push_delivery`'s silent `Ok(false)` sits ~120 lines from
`persist_mount_state`'s carefully-logged `Ok(false)`, with no obvious reason for
the two to differ. Same for the branch drift: the two resolutions are in
different crates and nothing puts them side by side.

A refactor should be planned before further changes land here.
