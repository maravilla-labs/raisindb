# Adversarial review of read-index-resolve-plan.md

Three critics (history/branch, replication, ops/migration). Fixes here are binding amendments to the plan.

(1) Replication applies revisions in order. It does not: apply_replicated_upsert has no check that the incoming revision is newer than what is stored, and its own comment names out-of-order catch-up. (2) load_latest_node is a usable "old" baseline. It
- Phase 7 delta writer: the replication baseline is the NEWEST stored version, not the version just before the incoming revision. Replication applies out-of-order revisions with no guard, so skip-unchanged corrupts HEAD on replicas.
  FIX: The delta writer may skip only when the incoming revision is strictly greater than the baseline's revision, AND the baseline is the version at or below the incoming revision (read bounded by `revision`, not latest). Otherwise it must fall back to a full put. Add a property test: oracle stage 3 with shuffled, interleaved two-origin oplogs, not single-origin replay.
- Phase 7/2.8 baseline decode: load_latest_node deserializes NODES blobs as `Node`. Repository-written blobs are StorageNode, which has no `path` field, so `path` defaults to "". Phase 10 widens this to every SQL/WS write.
  FIX: Phase 2.8 must replace the decode, not only the seek. Route load_latest_node through the shared deserialize_node_with_path (materializing NODE_PATH at the baseline's revision), and make that function the only baseline reader for Phase 7, Phase 8 and the Phase 12 sync_node. Land this before Phase 7 and before Phase 10.
- Phase 2.8 workspace-scoped seek: the workspace is always present because it is defaulted, so the 'slow path for callers with no workspace' never runs. A node whose op carries no workspace (older peers in a mixed-version cluster) gets old_node=None, and stale path/property/spatial entries are never tombstoned, silently.
  FIX: Distinguish an explicit workspace from a defaulted one. On a scoped miss, fall back to the branch scan with a warn! counter (a miss cannot be told apart from a wrong workspace). Remove the fallback only after a release in which the counter stayed at zero cluster-wide.
- Phase 9 run-collapse is not lossless in a multi-master cluster. Collapse assumes no entry will ever be inserted below existing entries, but out-of-order replication and the Phase 2 repairs (tombstones written at historical revisions) do exactly that.
  FIX: Collapse may only touch entries strictly below a cluster-wide causal-stability watermark (the minimum HLC that every peer has applied and acknowledged), never 'per node' at will. All historical-revision repair jobs (Phase 2.1, 2.2, Phase 10 backfill) must complete before collapse is enabled, and collapse must refuse to run while a repair job is pending. Under KEEP_ALL it must not run by default (reverse D7) until the watermark exists.
- Checkpoint ingest is a put-merge of every CF from the peer and emits no events. One-shot data repairs are silently undone by a later checkpoint from an unrepaired or older peer, and nothing re-runs them.
  FIX: For 2.2, make readers treat a one-byte `\x00` value as a tombstone permanently: one shared is_tombstone used by every PATH_INDEX reader. Keep the data repair as cleanup only, never as the fix. More generally, every 'repair job' in the plan must be either reader-tolerant, or re-triggered by the checkpoint ingest hook (the place that already calls invalidate_all_derived_caches).
- Phase 12 adds a new CF and breaks mixed-version clusters and binary rollback. An older binary cannot open a DB containing an unknown CF, and an older node cannot ingest a checkpoint from a newer node.
  FIX: Ship the CF registration (an empty CF, added to all_column_families) one release BEFORE any writer, and make the ingestor skip and warn on unknown CFs. State explicitly that downgrading below the registration release is unsupported, or add the CF to an 'open-if-present' list in the old release first.
- Rebuild and repair fan-out is unspecified. Admin-triggered jobs run on the one node that received the request; job dedup is per-process, and there is no replicated 'rebuild requested' op. The result is N-1 nodes that stay broken and report nothing.
  FIX: Pick one mechanism and name it in the plan: either (a) replicated config ops (UpdateRepository for default language and for localized_slug.property_pattern) enqueue the rebuild on REMOTE apply too, which puts the trigger on the 'local+remote' side of node_handlers.rs:133/162; or (b) an admin endpoint that fans out to every peer and reports per-node status. Add a per-node state record so the console can show which nodes have not repaired.
- Phase 12 gate staleness: a RepositoryConfig pattern change, or a default-language change replicated from a peer, leaves lname_state Ready, so lookups serve stale slugs instead of falling back. built_from_rev alone does not detect a config change.
  FIX: Store a fingerprint of (property_pattern, default_language, fallback chain) in lname_state and fail closed on a mismatch, the compound template. Enqueue the rebuild from the replicated UpdateRepository apply as well as the local admin path.
- Phase 12 sync_node under out-of-order apply leaves phantom slugs. The reverse row read is the NEWEST one, so an older replicated slug write puts a live forward key at the older revision that no newer revision ever tombstones.
  FIX: sync_node must read the reverse rows bounded by the incoming revision. When it applies below the latest reverse row, it must also write a tombstone for its own forward key at the next-newer reverse row's revision, so the newer state stays authoritative. Add the case to the interleaved-oplog oracle.
- Phase 2.5 replica compound NotBuilt marker: concurrent with a compound rebuild, the rebuild's final Ready overwrites a NotBuilt set by an upsert it never saw. Every replicated upsert after a rebuild flips the replica back to NotBuilt, so replicas sit permanently on scans. Per-call store caches are not shared with the applicator.
  FIX: The marker must carry a monotonic generation (or the applying revision), and the rebuild must CAS Ready only if no newer marker exists. State that Phase 2.5 makes replica compound queries scan-only until Phase 8.3. Find indexes via list_for_workspace (state records) and never via a NodeType read in the apply path. Phase 8.3 needs a cold-cache rule: unresolved definitions mean mark NotBuilt plus enqueue, never skip.
- Phase 7 loses self-healing on replicas that already hold incomplete entries. The replica writer historically omitted IS_A/HAS_MIXIN membership; with skip-unchanged, unchanged membership is never written again, and a sampling verify job leaves most holes in place.
  FIX: Make a full property-index rebuild on EVERY node (via the fan-out mechanism above) a precondition of enabling index.skip_unchanged. Alternatively, the delta writer does a full put whenever the per-node state record says 'built by pre-Phase-7 writer'.
- Phase 2.1 claims the replicated delete already has the parent id. It does, but the shared tombstoner is fed node.parent (the NAME) whenever the peer's node carries one, so the fix will not reach replicas unless the id is preferred.
  FIX: Change the tombstoner signature to take an explicit parent_index_id (Option) and have the replicated delete pass parent_id unconditionally. Add the test `replicated_delete_tombstones_by_parent_id`.
- Phase 11 rollout: the OpType enum has no catch-all variant, so an older binary cannot decode a new op. The admin 'resync translations' job and any env-flag flip before every node, including persisted oplogs, is on release 1 will wedge peers. Once release 2 emits, rolling back is one-way.
  FIX: The resync job must emit the LEGACY op while RAISIN_REPLICATION_EMIT_TRANSLATION_V2 is unset. Document that downgrading below release 1 after the flag is set is unsupported, because persisted oplog entries become undecodable. Consider adding an Unknown catch-all variant in release 1 so future ops degrade to skip-and-warn.

- Phase 12 rollback is broken: adding the localized_name_index CF makes the previous binary unable to open the database. The plan claims 'Turn the feature flag off. The CF is inert'.
  FIX: Ship a release N-1 that already declares the CF, or that opens every CF from DB::list_cf generically, before any release creates it. Add a downgrade test: open the DB with the old CF list after the new binary has run. Apply the same rule to any other new CF.
- Phase 10 rollback is unsafe. After NODE_PATH has been backfilled or written for SQL/WS nodes, a downgraded binary's put_node writes full-Node blobs and no NODE_PATH. Reads then materialize the stale path from NODE_PATH. This is the plan's own stale-path bug, made universal.
  FIX: Either make the read path prefer an embedded blob path whenever the blob carries one, shipped one release before Phase 10, or declare Phase 10 plus its backfill forward-only and gate it. Add a test that downgrades, renames through the old put_node, and reads back.
- Repair and backfill jobs (Phase 2 order tombstones, merge \x00, REFERENCE rebuild, Phase 10 backfill, Phase 12 rebuild) are specified as additions to the existing rebuild routine. That routine loads every node of a workspace into memory and commits one WriteBatch. On tens of GB this means OOM, multi-GB batches and write stalls. D11 'automatic in the next minor' makes every node run them at boot simultaneously.
  FIX: Require streaming iteration with bounded batches (for example 4–16 MB), a persisted resumable cursor, a rate limiter or low IO priority, a disk-headroom precheck, per-branch progress reporting, and never running at boot or on all nodes at once. Add a memory-bound test over a large synthetic workspace. D11 must stay admin-triggered.
- Merge apply is a mirrored write funnel the plan only half fixes. write_resolved_node and write_resolved_deletion write no ORDERED_CHILDREN entries or tombstones, no NODE_PATH tombstone on delete, and no UNIQUE, COMPOUND or translation entries. They do not call tombstones::tombstone_node. A merge-created or merge-moved node is missing from CHILD_OF. A merge-deleted node stays listed and keeps has_children true. Phase 2 repairs these symptoms while the source keeps producing them.
  FIX: Add a Phase 2 item: route merge deletion through tombstones::tombstone_node, and merge upsert/move through the shared ordered-children and NODE_PATH writers, before running any repair. Add merge_resolution_keeps_child_listing_consistent, covering create, move and delete. Otherwise the repair has to run forever.
- Checkpoint bootstrap ships every CF, including derived indexes and INDEX_STATUS, so 'nothing derived replicates' and 'repairs run locally per node' do not hold. A replica bootstrapped from an unrepaired peer inherits the corrupt ORDERED_CHILDREN and \x00 PATH_INDEX tombstones. It also inherits that peer's state records (Ready or NotBuilt, lname_state, compound). A new-binary peer can ship a CF that an older receiver cannot open.
  FIX: For every repair and new CF, state what checkpoint transfer does. Repairs must be idempotent and detect corruption from the data, never from 'done' flags. State records must be revalidated after ingest. Exclude new CFs from checkpoints across mixed versions, or version-gate them. Add a test that bootstraps from an unrepaired peer and then runs the repair.
- Phase 1 misses at least one behavioural consumer of storage-populated has_children. Package export decides between the folder layout (.node.yaml) and the file layout from node.has_children. Once storage returns None, a non-folder node with children is exported as {name}.yaml next to a {name}/ directory of children. The archive layout changes silently.
  FIX: Grep every `.has_children` read, not only the 33 get callers. Switch package_builder to an explicit has_children probe or to the collected-set membership. Add a golden package-export test for a non-folder node with children. List the functions callbacks (raisin-functions/.../callbacks/nodes.rs uses storage.nodes() directly) and MCP surfaces, and decide whether each keeps has_children.
- Phase 2 item 5 (mark compound NotBuilt on every replicated upsert) interacts with the compound build handler, which takes a cluster-wide lease and skips with 'being built elsewhere'. A replica marked NotBuilt may never rebuild locally, because the lease is held by the node that does not need the build. Each replicated upsert re-marks NotBuilt anyway, so compound queries on replicas fall back to scans until Phase 8. The plan's rule that 'rebuild jobs take no lease' contradicts existing code it does not mention changing.
  FIX: Remove the cluster lease from the compound build, or scope it per node (the lease key must include the node id), as part of Phase 2. Measure replica query latency under item 5. Prefer pulling Phase 8 step 3 (replica compound writes) forward over shipping a permanent replica scan fallback.
- Phase 7 delta writer: baseline 'replication's load_latest_node' is wrong for out-of-order or LWW-applied ops. When an op at revision r arrives after a newer one is already applied, a delta against the latest version writes live puts at r for values that nothing at a later revision tombstones. The result is phantom HEAD matches. The ORDERED_CHILDREN 'point read of the exact key' is also impossible, because the key carries the entry's write revision as well as the label.
  FIX: Define the baseline as the newest version strictly below the write revision, and handle the case where a newer version exists by skipping or recomputing the index for the newer state. Add the test replicated_op_older_than_head_does_not_leave_live_entries. Replace the exact-key point read with a (parent, label) prefix seek filtered by child id.
- Phase 6 removes the cross-value tombstone set before the writers are fixed or repaired. Orphan live entries from historically buggy writers (the replica writer missing membership entries, merge apply, the old in-place writer) remain. The plan claims the residual filter masks them, but pseudo-properties (node_type, __name, created_at/updated_at) have a residual exemption, so orphans there become phantom rows at HEAD and in COUNT.
  FIX: Before switching readers, run a report-only orphan detector on a prod snapshot that compares the HEAD index against the node blobs for pseudo-properties. Keep a residual check for pseudo-properties until the PROPERTY_INDEX rebuild or verify job has reported clean, or gate the new reader on a per-workspace state record.
- Phase 9 and the Phase 2 repairs do not account for disk use. RocksDB deletes add markers, so disk grows until compaction. A full compact_range on a CF of tens of GB needs temporary space roughly equal to the CF. Checkpoints hard-link SSTs, so retained backups pin the old files. Prod already holds about 207 GB of backups beside the data dir.
  FIX: Require a free-space precheck, at least 2× the CF size, against the data volume. Compact by key range in bounded slices with a rate limiter. Schedule outside the backup window. Document that the reclaimed space only appears after backup retention rotates. Report the bytes the dry run expects to reclaim.
- The Phase 0b oracle is not independent for ordering and paths. It 'reconstructs the tree from parent links plus ordered-children labels', but Node.parent is the parent NAME, not an id or path, so the tree is ambiguous. StorageNode blobs carry no path either, so the oracle must read NODE_PATH, which is itself under test (Phase 10). And reading ORDERED_CHILDREN to compute __order means editorial order is checked against itself. Marking failing templates #[should_panic] also passes on any panic, which masks new regressions in exactly those templates.
  FIX: The oracle should track tree and order from its own op log, the operations it generated: parent ids, explicit sibling order. It should also assert the invariant that Node.order_key equals the CF label. Replace #[should_panic] with a named expected-failure list whose expected results are asserted, and fail the build if a listed template unexpectedly passes.
- Phase 2's ORDERED_CHILDREN subtractive repair is under-specified for prod history. It must find entries whose child was deleted by scanning NODES tombstones, which existing helpers do not return (scan_nodes returns live nodes). It must tombstone the label the entry actually used, which can differ from the deleted node's order_key because of legacy drift and merge verbatim copies (see project_ordering_across_branches). It must run per branch, including forks taken after the delete that copied the untombstoned entry. Until it runs, the Phase 1 'continue scanning on a dead hit' probe is O(deleted children) per call on parents with many deleted children, such as Studio per-run job nodes.
  FIX: Have the repair iterate ORDERED_CHILDREN per parent, verify each (label, child) against the child's NODES state at HEAD, and tombstone the exact stored key's (label, child) at the child's delete revision. Cap the has_children probe's dead-hit scan, falling back to a bounded answer plus a warn and an enqueued repair. Add a fork-after-delete repair test.

That security hole sits behind Phase 1 and Phase 2 and a product decision (D1) with an optional legacy flag. Phase 12's `alternates{locale: path}` can leak paths in locales where the node is hidden.
  FIX: Ship RESOLVE target RLS as a standalone fix first, independent of the frontier refactor, and make any legacy flag default to enforced. Pass the statement snapshot into graph_resolver. - Phase 7 skip-unchanged is incompatible with merge's KEY-LEVEL replay. merge/apply.rs:1-17 and three_way.rs (update_head then copy_branch_indexes) replay the source branch's index entries into the target at their ORIGINAL revisions. resolution.rs:173-209 writes the resolved node at the merge revision M first, then copies (resolution.rs:388-392). Under Phase 7's baseline (the 'TARGET-branch old node'), a KeepOurs resolution with slug=A unchanged is skipped. The copy then lands the source's T(A,r5). The target's live A entry now sits at its creation revision r1 < r5, because skip never re-put it. So `properties->>'slug'::String='A'` loses the node at HEAD, while the source's live(B,r5) still matches. The same failure hits ORDERED_CHILDREN: write_resolved_node (apply.rs:90-230) writes no ordered entry at all. Once Phase 7 stops re-putting the target's label, a KeepOurs on a child that was reordered on the source shows the THEIRS position. That violates the 'order_key == CF label' invariant.
  FIX: Merge resolution must never use the delta or skip writer. At M, do a full put of every index, ORDERED_CHILDREN included. Tombstone the UNION of the values indexed by base, target head and source head, not just target-old vs new (today's add_stale_* calls leave the source side's values live: an existing bug that should be fixed in Phase 2). Add tests: merge_keep_ours_after_skip_unchanged_property_still_matches, merge_keep_ours_preserves_target_order_label, and merge_keep_ours_source_only_value_not_matched.
- Phase 7 computes the replication delta against load_latest_node. In multi-master, concurrent writes can arrive out of HLC order. Example: a replica applies r3 (slug=B) and then r2 (slug=B) arrives. The baseline is r3, so r2 counts as 'unchanged' and nothing is written at r2: no T(A,r2) and no live(B,r2). Time travel at r2 then returns slug=A, which is wrong. A full put has no such dependency on the baseline.
  FIX: Take the baseline as the node version immediately BEFORE the incoming revision (newest < rev), not the latest. If a newer version already exists, either do a full put at rev or emit tombstones relative to the predecessor and leave the successor's entries alone. Add an oracle stage-3 case with permuted apply order. Better still: keep full puts on the apply path until the oracle proves the delta there.
- Phase 7's claim 'Copy and cross-branch stage go through create (old = None)' is wrong for stage. stage_cross_branch_entry is an upsert with old_dst (stage.rs:114-145,163-185). Today it already tombstones only compound and unique entries from old_dst. It never tombstones PROPERTY_INDEX or REFERENCE_INDEX values that the source removed, so a publish leaves stale positives on the publish branch. Running the delta writer with old=None keeps that leak forever.
  FIX: Pass old_dst as the baseline in stage. Add test promote_removed_property_not_matched_on_publish_branch. Treat 'old=None' as legal only when the target id provably has no live version on the target branch.
- Phase 7 and Phase 9 change the answer of get_last_order_label's fallback scan. It chooses the 'last' label by the HIGHEST REVISION seen per label, not by the lexicographically greatest live label, and it skips tombstones without recording the label, so an older live entry of a deleted child counts again. Skip-unchanged (no re-put) and run-collapse (deleting newer identical entries) both shift those revision maxima. On a metadata-cache miss, the next append can then mint a label that sorts before existing siblings or collides with one, which corrupts editorial order.
  FIX: Before Phase 7 or 9 touch ORDERED_CHILDREN, rewrite these readers to use (label, child) newest-wins with tombstones honoured and return the lexicographically max LIVE label. Add them to the 0b oracle templates.
- Phase 9's 'lossless; pins irrelevant' holds only when nothing inserts entries at historical revisions. The plan adds exactly such writers: the Phase 2 ORDERED_CHILDREN repair writes T at the child's old delete revision, and the Phase 12 rebuild writes at each node's current revision. Concrete case: a child is deleted at rdel, where the tombstone was mis-keyed and so is missing, then re-created at r3 with the same label and name. Collapse sees live(r1), live(r3) as identical and deletes r3. The repair then inserts T(rdel), and the re-created child disappears at HEAD. A collapse decision is also invalidated by any concurrent historical-revision insert between its read and its delete.
  FIX: Make Phase 9 hard-depend on completion of every Phase 2 repair for that CF and branch (record it in the state record). - The Phase 2.1 repair cannot find all of its targets, and it resolves the parent at the wrong time. (a) The ORDERED_CHILDREN tombstone is keyed by node.parent, the parent NAME (core_tombstones.rs:76-89). The repair resolves the parent id via a PATH_INDEX read of parent_path(), which is HEAD-bounded. In a cascade delete the parent is gone, or its path is now owned by a different node. (b) history_gc with drop_orphan_tombstones (mod.rs:226-235) can already have removed the child's NODES versions and tombstone, while the stale live ORDERED_CHILDREN entry survived, because it is its own group's newest. - Phase 4's rule 'read NODE_PATH at the snapshot, never at the blob's revision' returns stale paths for put_node-written nodes. The transaction path stores a full Node blob with its path (create/storage.rs:54) and writes no NODE_PATH. deserialize_node_with_path tries StorageNode first; a full Node blob also parses that way (unknown 'path' field is ignored), so the NODE_PATH entry wins (path_materialization.rs:138-150). Phase 10's backfill only covers 'nodes with no NODE_PATH entry', which is exactly NOT the affected population, and it says 'no history is rewritten', so time travel to r2 stays wrong forever.
  FIX: Path rule for all readers (Phase 1's merged materialize_path and Phase 4's batch_get): take the newer of (NODE_PATH newest ≤ snapshot) and (an embedded blob path at the blob's revision), comparing revisions. The NODE_PATH entry only wins when its revision is ≥ the blob's, which covers ancestor moves. - The 0b oracle derives truth from cf::NODES. It is therefore blind to bugs that distort NODES-level history itself. Two examples: merge replays the source's NODES at original revisions, so the target 'had' the source's edits before the merge; and versionable=false rewrites a pre-fork revision in place, which silently changes the target's state at the fork pin and at every revision ≥ R0. Phases 6-9 are declared 'guarded by the oracle', but the oracle would agree with corrupted history.
  FIX: Add an independent in-memory reference model driven by the generated operation sequence (including merge with resolutions, versionable=false updates and fork). Compare both NODES and the indexes against it. Explicitly model versionable=false as 'no history', so those nodes are excluded from historical-revision assertions instead of making them pass vacuously.
- Phase 7 says 'versionable=false: the reused-revision tombstone overwrites the original key, which is fine'. That is only true when the entry being superseded sits at exactly R.
